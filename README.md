# PBX Doc

Веб-приложение для ведения документации по транкам, маршрутам, сценариям
(диалплану) и номерам/экстеншенам Asterisk. Три роли пользователей и полный
журнал аудита изменений.

Написано на чистом PHP (без Composer и сторонних фреймворков) + MySQL/MariaDB.
Так проще развернуть на любом обычном хостинге с PHP и MySQL — не нужен
`composer install` и доступ в интернет с сервера.

## Возможности

- **Транки** — SIP/PJSIP/IAX2 подключения к операторам: тип, хост, контекст,
  статус, описание. На карточке транка отображается список привязанных к
  нему номеров.
- **Маршруты** — правила маршрутизации (входящие/исходящие), шаблон номера,
  привязка к транку.
- **Сценарии** — диалплан/IVR: контекст, описание, код `extensions.conf`.
- **Номера/экстеншены** — делятся на **внутренние** и **внешние**.
  Для всех номеров (и внутренних, и внешних) можно указать владельца и
  подразделение (из справочника «Подразделения»); поле «Подразделение»
  расположено между «Владелец» и «Статус». Для внешних номеров доступен
  свой набор типов (Городской (DID) — по умолчанию, Сотовый (DID),
  CallTracking, Other) и привязка к юрлицу, провайдеру (список
  провайдеров фильтруется по выбранному юрлицу) и транку. Поле
  «Связанный сценарий» и «Контекст диалплана» показываются в одной
  строке. Если у внешнего номера выбран тип CallTracking, поле
  «Подразделение» вместо стандартного места показывается рядом с полем
  «Цель» — выбор департамента фильтрует список доступных целей из
  справочника «Calltracking» (у каждой цели свой департамент).
  Страница списка номеров (`/extensions`) построена как 5 вкладок:
  **Внешние** (Номер/Тип/Провайдер/Транк/Владелец/Подразделение/Цель/
  Статус/Изменён), **Внутренние** — только тип «Внутренний»
  (Номер/Владелец/Подразделение/Статус/Изменён), **Очередь**, **Групповые**
  и **Служебные** — каждая показывает только номера своего типа с тем же
  набором колонок, что и «Внутренние». Поиск на этой странице живой
  (AJAX, без перезагрузки) и начинает фильтровать список от 2 символов —
  короче показывается весь список текущей вкладки; строка поиска
  синхронизируется с URL (`?tab=...&q=...`).
  Дубли номеров запрещены для внутренних номеров (проверка при вводе —
  подсвечивает поле и показывает, у какого номера конфликт, плюс жёсткая
  проверка на сервере при сохранении); для внешних номеров дубли
  разрешены. На странице внутреннего номера с типом «Внутренний»
  показывается карточка «Состоит в очередях/группах» — список всех
  очередей и групп обзвона, куда он включён как участник.
  Типы внутренних номеров: **Внутренний**, **Очередь (Queue)**,
  **Группа обзвона (Ring Group)**, **Служебный номер**.
  - Для типа **Очередь**: поля «Связанный сценарий»/«Контекст диалплана»
    скрыты (не применимы); появляются состав очереди (только номера типа
    «Внутренний», с изменяемым порядком через интерактивный поиск и
    кнопки ↑/↓), метод обзвона участников (6 стратегий Asterisk: ringall,
    leastrecent, fewestcalls, random, rrmemory, linear), настройки для
    операторов (время дозвона, время отдыха, приём звонков во время
    разговора), настройки для вызывающего абонента (музыка/сигнал
    ожидания, фоновая музыка MOH и рекламная фраза — выбор из справочника
    «Музыка» или загрузка своего файла прямо из формы, оповещения о
    позиции/времени ожидания) и маршрутизация звонков при сбоях (два
    сценария перевода — по таймауту ожидания и при отсутствии операторов,
    с интерактивным поиском цели среди сценариев и номеров).
  - Для типа **Группа обзвона**: состав группы (тот же picker, что и у
    очереди), метод обзвона (2 стратегии: всем одновременно или по
    порядку) и настройки для операторов (время дозвона, время отдыха).
  - Номер с типом «Внутренний», входящий в состав какой-либо очереди или
    группы обзвона, нельзя удалить или сменить ему категорию/тип, пока
    он не убран из состава.
- **Подразделения** — справочник отделов компании, используется для
  привязки внутренних номеров.
- **Оборудование** — справочник шлюзов, базовых станций IP DECT,
  IP-телефонов и софтфонов: расположение, тип, IP-адрес, описание.
  Типы оборудования (категория, название, модель, бренд) хранятся во
  вложенном справочнике «Типы оборудования».
- **Юрлица** — справочник обслуживаемых юридических лиц: наименование, ИНН.
- **Провайдеры** — справочник поставщиков связи: наименование,
  телефон техподдержки, примечание, до 3 контактных менеджеров (имя +
  телефон) и список обслуживаемых юрлиц (многие-ко-многим — один провайдер
  может обслуживать несколько юрлиц). Для каждой привязки к юрлицу можно
  указать ответственного менеджера и **№ договора** (договор относится к
  конкретному юрлицу, а не к провайдеру в целом).
- **Calltracking** — справочник целей коллтрекинга: подразделение (из
  справочника «Подразделения») и цель (текст). Используется в поле «Цель»
  внешних номеров с типом CallTracking.
- **Музыка** — справочник аудиофайлов WAV/MP3 (фоновая музыка и рекламные
  фразы для очередей): загрузка файла (поддерживаются русские названия),
  список по дате и времени добавления, прослушивание прямо в браузере
  (плеер `<audio>` с перемоткой), удаление доступно только администратору
  и только если файл нигде не используется — если используется, показывается,
  в каких номерах, и удаление блокируется.
- **Три роли:**
  - **Администратор** — полный доступ: создание/редактирование/удаление
    всех сущностей, управление пользователями и ролями.
  - **Пользователь** — может добавлять и редактировать транки, маршруты,
    сценарии и номера, но не может их удалять и не видит раздел
    «Пользователи».
  - **Наблюдатель** — доступ только на просмотр (включая историю изменений).
- **Журнал аудита** — при открытии карточки любой сущности (включая
  провайдеров — с резюме по менеджерам и привязанным юрлицам) видно, кто и
  когда её менял, с постатейным сравнением «было → стало». Также на главной
  странице есть общая лента последних изменений по всем сущностям.
- Поиск по спискам, CSRF-защита форм, хэширование паролей (bcrypt),
  защита от удаления/разжалования последнего администратора.

## Требования к серверу

- PHP 8.1+ с расширениями `pdo_mysql`, `mbstring`, `fileinfo` (обычно
  включены по умолчанию на любом хостинге; `fileinfo` нужен для проверки
  формата файлов в справочнике «Музыка»).
- MySQL 5.7+ / MariaDB 10.3+.
- Apache с `mod_rewrite` или Nginx + PHP-FPM.
- Composer **не требуется** — в проекте нет внешних зависимостей.

## Установка

### 1. Скопируйте файлы на сервер

Разместите содержимое архива в отдельной папке, например
`/var/www/pbxdoc`. Структура:

```
pbxdoc/
├── public/          ← это должно быть DocumentRoot сайта!
├── src/              ← код приложения (контроллеры, модели, ядро)
├── templates/        ← шаблоны страниц
├── database/         ← SQL-схема и начальные данные
├── .env.example
└── README.md
```

**Важно:** веб-сервер должен смотреть именно на папку `public/`, а не на
корень проекта. Если направить хостинг на корень, файлы `.env`, `src/` и
`database/*.sql` окажутся доступны по прямой ссылке — это утечка паролей
от БД и структуры базы.

### 2. Создайте базу данных

```sql
CREATE DATABASE pbxdoc CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'pbxdoc'@'localhost' IDENTIFIED BY 'придумайте_пароль';
GRANT ALL PRIVILEGES ON pbxdoc.* TO 'pbxdoc'@'localhost';
FLUSH PRIVILEGES;
```

Накатите схему и создайте администратора:

```bash
mysql --default-character-set=utf8mb4 -u pbxdoc -p pbxdoc < database/schema.sql
mysql --default-character-set=utf8mb4 -u pbxdoc -p pbxdoc < database/seed.sql
```

> Флаг `--default-character-set=utf8mb4` обязателен — без него клиент mysql
> по умолчанию использует latin1, и русский текст в seed-файлах превратится
> в «кракозябры». (Сами SQL-файлы дополнительно подстраховываются командой
> `SET NAMES utf8mb4`, но флаг всё равно рекомендуется для любых ваших
> собственных SQL-скриптов.)

По желанию — демонстрационные данные (несколько примеров транков,
маршрутов, сценария и номеров), чтобы сразу увидеть, как выглядит
заполненное приложение:

```bash
mysql --default-character-set=utf8mb4 -u pbxdoc -p pbxdoc < database/demo_seed.sql
```

### 3. Настройте .env

```bash
cp .env.example .env
```

Отредактируйте `.env` — впишите параметры подключения к БД:

```
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=pbxdoc
DB_USERNAME=pbxdoc
DB_PASSWORD=придумайте_пароль
APP_URL=https://pbx-doc.example.com
APP_DEBUG=false
```

`.env` должен лежать в корне проекта (рядом с `public/`, `src/`), не внутри
`public/`.

Для справочника «Музыка» также укажите `MUSIC_MAX_UPLOAD_MB` (по умолчанию
20 МБ) — и убедитесь, что `upload_max_filesize` и `post_max_size` в
`php.ini` не меньше этого значения (иначе PHP обрежет загрузку раньше, чем
сработает проверка приложения).

### 4. Настройте веб-сервер

**Apache** (файл `public/.htaccess` уже включён в проект, достаточно
`mod_rewrite`):

```apache
<VirtualHost *:80>
    ServerName pbx-doc.example.com
    DocumentRoot /var/www/pbxdoc/public

    <Directory /var/www/pbxdoc/public>
        AllowOverride All
        Require all granted
    </Directory>
</VirtualHost>
```

**Nginx + PHP-FPM:**

```nginx
server {
    listen 80;
    server_name pbx-doc.example.com;
    root /var/www/pbxdoc/public;
    index index.php;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_pass unix:/var/run/php/php8.1-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    }

    location ~ /\.(env|git) {
        deny all;
    }
}
```

Проверьте права на запись для процесса PHP — приложению нужны только права
на чтение файлов проекта (записи на диск не требуется, все данные хранятся
в БД).

### 5. Первый вход

Откройте сайт в браузере и войдите под учётной записью администратора по
умолчанию:

- **Email:** `admin@example.com`
- **Пароль:** `admin123`

**Сразу после входа смените пароль** (раздел «Пользователи» →
редактирование администратора) или создайте себе новую учётную запись
администратора и удалите/деактивируйте стандартную.

## Роли и права доступа — подробнее

| Действие                                   | Администратор | Пользователь | Наблюдатель |
|---------------------------------------------|:---:|:---:|:---:|
| Просмотр транков/маршрутов/сценариев/номеров | ✔ | ✔ | ✔ |
| Просмотр истории изменений                   | ✔ | ✔ | ✔ |
| Создание/редактирование записей              | ✔ | ✔ | — |
| Удаление записей                             | ✔ | — | — |
| Управление пользователями и ролями           | ✔ | — | — |

Логика ролей находится в `src/Core/Auth.php` (методы `canEdit()`,
`canDelete()`, `requireAdmin()` и т.д.) — при необходимости права легко
скорректировать под ваши процессы (например, разрешить «Пользователю»
удаление).

## Журнал аудита

Каждое создание, изменение и удаление транка, маршрута, сценария или номера
пишется в таблицу `audit_logs`: кто, когда, какое действие и какие именно
поля изменились (старое и новое значение). Открыв карточку записи, вы
увидите блок «История изменений» с полной хронологией. На главной странице
собрана общая лента последних изменений по всем разделам.

Изменения пользователей (создание, смена роли, деактивация) тоже
логируются — эти события можно найти в той же таблице `audit_logs` с
`entity_type = 'user'`.

## Миграции (обновление уже развёрнутой установки)

Если приложение уже установлено и в базе есть данные, **не** перезаливайте
`database/schema.sql` заново — вместо этого применяйте файлы из
`database/migrations/` по порядку (каждый выполняется один раз и
безопасен для повторного запуска — использует `information_schema` и
`ON DUPLICATE KEY`/условные проверки).

После `git pull` выполните для каждой новой миграции:

```bash
mysql --default-character-set=utf8mb4 -u pbxdoc -p pbxdoc < database/migrations/0001_departments_equipment_extension_categories.sql
```

Применяйте миграции по порядку — каждую в своём файле:

```bash
mysql --default-character-set=utf8mb4 -u pbxdoc -p pbxdoc < database/migrations/0001_departments_equipment_extension_categories.sql
mysql --default-character-set=utf8mb4 -u pbxdoc -p pbxdoc < database/migrations/0002_legal_entities_providers_extension_links.sql
mysql --default-character-set=utf8mb4 -u pbxdoc -p pbxdoc < database/migrations/0003_calltracking_provider_contract.sql
mysql --default-character-set=utf8mb4 -u pbxdoc -p pbxdoc < database/migrations/0004_music_and_queue_settings.sql
```

Миграция `0001_departments_equipment_extension_categories.sql`:
- создаёт таблицы `departments`, `equipment_types`, `equipment`;
- добавляет в `extensions` колонки `category` (внутренний/внешний) и
  `department_id`;
- автоматически заполняет `category` для уже существующих номеров:
  `did` → `external`, остальные типы → `internal`. Поле `department_id`
  у существующих номеров остаётся пустым — при необходимости укажите
  подразделение вручную через интерфейс.

Миграция `0002_legal_entities_providers_extension_links.sql`:
- создаёт таблицы `legal_entities`, `providers`, `provider_managers`,
  `provider_legal_entities`;
- добавляет в `extensions` колонки `legal_entity_id`, `provider_id`,
  `trunk_id`;
- переносит старое значение типа внешнего номера `did` в новое значение
  `did_city` («Городской (DID)») — набор допустимых типов для внешних
  номеров изменился на: `did_city`, `did_mobile`, `calltracking`, `other`.

Миграция `0003_calltracking_provider_contract.sql`:
- добавляет колонку `contract_number` в `provider_legal_entities` и
  переносит туда значения из старой колонки `providers.contract_number`
  (по одной строке на каждую существующую привязку юрлица к провайдеру),
  после чего удаляет `providers.contract_number` — теперь № договора
  указывается для каждого юрлица провайдера отдельно, а не для провайдера
  в целом;
- создаёт таблицу `calltracking_targets` (справочник «Calltracking»);
- добавляет в `extensions` колонку `calltracking_target_id` (заполняется
  только для внешних номеров с типом CallTracking).

Миграция `0004_music_and_queue_settings.sql`:
- создаёт таблицу `music_files` (справочник «Музыка»);
- создаёт таблицу `extension_queue_settings` (настройки очереди/группы
  обзвона, 1 к 1 с `extensions`, для type = queue|ivr);
- создаёт таблицу `extension_group_members` (упорядоченный состав
  участников очереди/группы обзвона).

После накатки миграции 0004 убедитесь, что папка `storage/music/`
существует на сервере и доступна на запись пользователю веб-сервера:

```bash
mkdir -p storage/music
chown www-data:www-data storage/music   # замените на пользователя вашего веб-сервера
```

На новых установках всё это уже включено в `database/schema.sql`, а папка
`storage/music/` уже присутствует в архиве — отдельно накатывать миграции
не нужно, только проверить права на запись.

## Безопасность

- Пароли хранятся в виде bcrypt-хэшей (`password_hash`), в открытом виде
  нигде не сохраняются.
- Все формы защищены CSRF-токеном.
- Сессии — httponly-cookie, `secure` включается автоматически при работе
  по HTTPS.
- Доступ к `.env`, `*.sql` и `*.md` из браузера закрыт правилами в
  `public/.htaccess` (при условии, что DocumentRoot — это папка `public/`).
- Файлы музыки хранятся в `storage/music/`, вне `public/` — извне они
  недоступны напрямую и отдаются только через контроллер (с проверкой
  авторизации).
- Обязательно используйте HTTPS в продакшене и смените пароль
  администратора по умолчанию.

## Переход на PostgreSQL (если понадобится)

Проект по умолчанию рассчитан на MySQL/MariaDB. Если в будущем захотите
перейти на PostgreSQL — понадобится:
1. Заменить DSN в `src/Core/Db.php` на `pgsql:host=...;dbname=...`.
2. Адаптировать `database/schema.sql` — в основном это замена
   `AUTO_INCREMENT` на `SERIAL`/`GENERATED ALWAYS AS IDENTITY` и
   `DATETIME ... ON UPDATE CURRENT_TIMESTAMP` на триггер (в PostgreSQL нет
   прямого аналога `ON UPDATE`). Типы данных (`VARCHAR`, `TEXT`,
   `TINYINT(1)` → `BOOLEAN`) в остальном совместимы.
Специально ничего MySQL-специфичного (вроде `ENUM`) в схеме не
использовано именно для упрощения такого переноса.
